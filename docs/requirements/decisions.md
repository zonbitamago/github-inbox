## D-004: 既製品と併用しつつ、通知と PR 一覧の両方を自作する

- 日付: 2026-11-26
- 決定: Gitify（OSS の GitHub 通知デスクトップアプリ）と GitHub Mobile は併用する。そのうえで、通知と PR 一覧の両方を自作する
- 理由: Gitify には自分に関わる PR の一覧がない。依頼者は Gitify を使いつつ、比較のためにも自作することを選んだ。GitHub Mobile は併用するが、作業中に見ている PC 側で気づける仕組みが別に必要
- 検討した他の案: 「Gitify を試してから作るか決める」「通知は Gitify に任せ、PR 一覧だけ作る」。いずれも採らなかった
- 影響: Gitify を比較の相手とする。比べる観点と時期は依頼者が ③ までに決める
- 更新（2026-11-26）: Gitify の併用と比較は D-006 でやめた。GitHub Mobile の併用と、通知・PR 一覧の両方を自作することは変わらない

## D-006: Gitify は使わない。アプリは普通のウィンドウを持ち、OS の切り替えで移れる形にする

- 日付: 2026-11-26
- 決定:

## D-008: CI の結果は、自分が起動した GitHub Actions のワークフローの完了まで

- 日付: 2026-11-26
- 決定: 出来事として扱う CI の結果は、自分が起動した GitHub Actions のワークフローの完了まででよい。GitHub Actions 以外の CI は扱わない
- 理由: GitHub の通知で CI の完了が届く範囲（通知の理由 `ci_activity`）を示し、依頼者が「OKです」と回答した
- 出典: https://docs.github.com/en/rest/activity/notifications#about-notification-reasons

## D-009: 立ち上がっていなかった間の出来事は、次に立ち上げたとき表示する。通知は出さない

- 日付: 2026-11-26
- 決定: アプリが立ち上がっていなかった間に起きた出来事は、次に立ち上げたとき出来事の一覧に表示する。それらにはデスクトップ通知を出さない
- 理由: 依頼者の言葉は「表示されれば通知自体は不要です」
- 未定: どこまで遡って表示するか（依頼者が ③ で判断）

## D-010: PR の一覧は「自分待ちの PR」と「直近に関わった PR」。どちらも github-prs の条件と期間にそろえる

- 日付: 2026-11-26
- 決定:
  - 自分待ちの理由は5つ（レビュー依頼に未対応／修正依頼あり／CI 失敗／承認済み（マージ待ち）／アサイン）。依頼者は4つの選択肢をすべて選び、「元の条件に揃えて欲しい」と添えた。「元の条件」は github-prs の条件を指すと確認した
  - 土台は github-prs と同じ `involves:@me` に、利用者へのレビュー依頼を加えたもの
  - 直近に関わった PR（github-prs と同じ範囲。closed・merged も含む）も分けて出す
  - 期間は既定7日で、利用者が変えられる。自分待ちの PR にも同じ期間をかける
- 理由: 依頼者の回答「3で期間は可変にできると良い。デフォルトは1週間としたい。」と、自分待ちの期間についての「同じ期間をかける」
- 承知していること: 更新が止まったまま期間を過ぎたレビュー依頼は、自分待ちの PR から消える（2026-11-26 時点で、レビュー依頼中の open の PR 14件のうち10件が7日以上更新なし）。これを示したうえで依頼者が選んだ
- 詳細: business-data.md 2.5・3.
- 更新（2026-11-26）: D-016 で、PR の一覧は分けずに1つにまとめ、自分待ちは理由のラベルで示すことにした

## D-011: 出来事は1件ずつ並べる。CI の結果は成功も失敗も扱う

- 日付: 2026-11-26
- 決定:
  - 1つの PR にコメントが3件付いたら、出来事も3件として並べる（1件のコメント・レビュー・依頼が出来事1件）
  - 自分が起動した GitHub Actions のワークフローの完了は、成功も失敗も出来事として扱う
- 理由: 依頼者の回答「3件として並ぶ」「成功も失敗も」
- 影響: GitHub の通知受信箱は PR・issue ごとに1件にまとまるため、出来事の単位と合わない。取り込み元は ⑦ で決める（business-data.md 5.）

## D-012: ③ やること整理での判断

- 日付: 2026-11-26
- 決定（依頼者の回答）:
  - 優先度: 参加中の PR への発言 M／チーム宛てのレビュー依頼 S／GitHub Discussions でのメンション C／自分待ちの PR の数をアイコンに出す S（D-013 で W に変更）／一覧の検索・絞り込み M／種類ごとのデスクトップ通知のオン／オフ M／表示言語の切り替え S（入れない場合は日本語）／ログイン時の自動起動を選べる S
  - 参加中の PR への発言の範囲: 自分がレビュー・コメントした他人の open の PR に付いた、他の人の新しいコメント・レビューすべて（「自分のコメントへの返信だけ」ではない）
  - CI の結果: 成功・失敗以外も含め、すべての値を出来事にし、GitHub の値の名前をそのまま出す
  - 自分待ちの理由「CI 失敗」: PR のチェックの総合結果（GitHub Actions 以外も含む）
  - 期間: 1〜30日の範囲で変えられる（既定7日）。立ち上がっていなかった間の出来事も同じ日数まで遡る
  - ウィンドウを閉じたら終了する
  - 新しい版はアプリが知らせ、各自が入れ直す（自動更新はしない）
  - 配る相手の PC には署名のないアプリを入れられる。署名はせず、OS の警告は手順書で案内する
- 承知していること: 閉じている間は出来事を受け取らず、デスクトップ通知も出ない。S1（5分以内）はアプリが立ち上がっている間の約束になる（requirements.md 5. #1）
- 手戻りタグ: 付けない。business-data.md・business-flow.md の更新は、②.5・②.6 で「③ で判断」と予定していた未定事項を埋めたもので、手戻りイベントではないため
- 変更: SAML SSO の有無の確認は、③ までに依頼者が行う予定だったが、認証方式と合わせて技術者が ⑦ で確かめることにした
- 詳細: requirements.md

## D-013: PR の一覧は手動で更新する。アイコンに数は出さない

- 日付: 2026-11-26
- 決定:
  - PR の一覧は、立ち上げたときと、利用者がリロードしたときに最新にする（F-20 を S から M へ）。自動で最新に保つことはしない（F-19 を M から W-12 へ）
  - Dock・タスクバーのアイコンに自分待ちの PR の数を出すのはやめる（F-21 を S から W-13 へ）
- 理由: 依頼者の言葉「F-19に関しては、手動で更新でOKです(リロードボタンがあるとか)。自動で最新に保つ必要はありません。」。一覧を自動で最新にしないとアイコンの数が古いまま残ると示したところ、「自分待ちのPRの数はアイコンに表示しないでOKとします。」
- 承知していること: 出来事でレビュー依頼などを知っても、リロードするまでその PR は自分待ちの PR に出ない（requirements.md 5. #8）
- その他: requirements.md の「AI案」の項目は、上記以外この内容で依頼者が確認した
- 手戻りタグ: 付けない。requirements.md の確認中（③ の中）での変更のため

## D-032: 出来事の一覧で、文字で探した語を強調する

- 日付: 2026-11-27
- 経緯: ⑭ S3b の実機の確かめで、依頼者が出来事の一覧の絞り込み（F-13）を使い、「探した文言が表示の中に含まれていれば、その文字を強調表示してほしい」と求めた（絞り込みそのものは正しく動いていた）
- 決定:
  - 文字で探したとき、行に出している文字のうち探す対象（対象のタイトル・リポジトリと番号・誰が・抜粋・CI の結果）の中で、探した語に当たる所を強調する。大文字と小文字は区別せず、空白で区切った語はそれぞれ強調する
  - 種類・リポジトリの選択だけで絞ったときは強調しない

  - リポジトリと番号は、探すときも表示と同じ形（`owner/name #番号`）で探す。見たままに強調できるようにするため
- 要件: F-13 の範囲の見た目の追加。受け入れ条件（AC-16）は変えない
