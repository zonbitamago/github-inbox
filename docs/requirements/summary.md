## 1. 何のために作るか

Slack が恒久的に使えなくなり、GitHub の「自分に関わる通知」が届かなくなった。そのため、相手を待たせる・自分の PR が止まる・通知受信箱やメールでは埋もれる・自分待ちが分からない、という4つの困りごとが起きている。

**GitHub 上で自分に関わる出来事に数分以内に気づき、自分待ちの PR を一覧でつかめるようにして、相手を待たせず、自分の PR も止めない。**

| 成功の合図 | 確かめ方（リリースの2〜4週間後） |
| --- | --- |
| S1 自分に関わる出来事に、発生から5分以内にデスクトップ通知で気づける | 種類が偏らないよう選んだ10件がすべて5分以内 |
| S2 1画面で自分待ちの PR が分かる | 自分待ちなのに PR の一覧で理由のラベルが付いていなかった PR が0件で、依頼者が「探し回らなくて済んだ」と評価 |

## 2. 誰が、どんな形で使うか

- 主な利用者は依頼者本人（Mac）。チームの希望者（10人前後のうち欲しい人。Mac と Windows が混在）にも配る
- 対象は github.com の Organization。管理者の承認は要らない
- **普通のウィンドウを持つデスクトップアプリ**。立ち上げたままにして、Mac では Cmd+Tab と AltTab アプリ、Windows では Alt+Tab で移る。メニューバーやタスクトレイには常駐しない
- ウィンドウを閉じたら終了する

## 3. 日々の流れ

1. チームメンバーがレビュー依頼・レビュー・コメント・メンション・アサインをする。自分の CI が終わる
2. 本アプリが5分以内に受け取り、出来事の一覧に載せ、デスクトップ通知を出す
3. 利用者はデスクトップ通知かアプリの切り替えで本アプリに移り、すぐ GitHub で開くか、後で一覧からまとめて片付ける
4. 区切りのよいときに PR の一覧を見て（必要ならリロードして）、自分待ちの PR を確かめる

希望者は、配布物と手順書を見てインストールし、自分の GitHub アカウントで認証して使い始める。新しい版が出るとアプリが知らせ、各自が入れ直す。

## 4. やること

### M 必須

- 自分に関わる出来事を受け取る: レビュー依頼・レビュー・コメント・CI の結果（すべての値をそのまま）・メンション・アサイン・参加中の PR への発言。bot の発言も含む
- 立ち上がっていなかった間の出来事も、次に立ち上げたとき一覧に出す（デスクトップ通知は出さない）
- 出来事ごとのデスクトップ通知。クリックで本アプリが前面に出る。種類ごと・bot の発言だけのオン／オフ
- 出来事の一覧、GitHub で開く、検索・絞り込み
- PR の一覧は1つ（直近に関わった PR。更新の新しい順、スクロールで全件）。自分待ちの PR には理由のラベル（レビュー依頼に未対応／修正依頼あり／CI 失敗／承認済み／アサイン）を付ける。GitHub で開く、検索・絞り込み（「自分待ちの理由あり」を含む）、リロード、一覧に出ている PR のリンクをまとめてコピー（github-prs の「Copy All Links」と同じ。週1回使う）
- 普通のウィンドウで切り替え対象に出る。閉じたら終了
- 各自の GitHub アカウントでの認証。Mac 用・Windows 用の配布物と手順書
- 非機能: 5分以内／PC を重くしない（ただし使い心地を優先）／GitHub の利用制限で止まらない／認証情報を平文や URL に置かない／GitHub には読み取りだけ／受け取れていないことが画面で分かる

### S できれば

チーム宛てのレビュー依頼、PR の一覧の期間の変更（1〜30日、既定7日）、出来事の一覧の日数を期間とは別に選ぶ（1〜30日、既定7日）、画面の並べ方（タブ／左右）を選ぶ、ログイン時の自動起動、表示言語の切り替え（日本語／英語）、サインアウト、新しい版の知らせ、ネットワークが戻ったら受け取りを再開

### C あれば

Discussions でのメンション、時間帯でデスクトップ通知を止める、PR のリンクを1件ずつコピー

### W 今回はやらない

済み／既読の管理（一旦）、アプリ内でのレビュー・承認・コメント、リポジトリ全体の活動、メニューバー・タスクトレイの常駐、デプロイのレビュー依頼、チーム全員への定着、PR の一覧の自動更新、アイコンの数、自動更新、署名、GitHub Mobile・Gitify との連携、複数アカウント、GitHub Enterprise Server・Linux

## 5. 承知している割り切り

依頼者がこれを知ったうえで選んだもの。合意の場で、もう一度「これでいく」かを確かめる。

| 割り切り | 理由・補い方 |
| --- | --- |
| 閉じている間は出来事を受け取らず、デスクトップ通知も出ない。S1 はアプリが立ち上がっている間の約束になる | 閉じたら終了する、を選んだ。閉じていた間の出来事は次に立ち上げたとき一覧に出る。自動起動（S）で立ち上げ忘れを防ぐ |
| 期間（既定7日）を過ぎたレビュー依頼は、PR の一覧から消え、自分待ちのラベルも見えなくなる（2026-11-26 時点で、レビュー依頼中の14件のうち10件が該当） | github-prs の条件と期間にそろえることを選んだ |
| どこまで出来事を見たかを、アプリは覚えない | 済み／既読は一旦管理しない |
| 出来事でレビュー依頼などを知っても、リロードするまで PR の一覧に出ない | PR の一覧は手動で更新する |
| 出来事が多くなる（参加中の PR への発言・CI のすべての結果・bot の発言） | 種類ごと・bot だけのデスクトップ通知のオフと、絞り込みで抑える |
| インストールや初回起動のときに OS の警告が出る | 署名しない。警告を越えて開く手順を手順書に書く |

## 6. 設計で確かめる技術リスク

| リスク | 確かめる工程 |

| 出来事を1件ずつ5分以内に受け取り、参加中の PR への発言も扱うと、GitHub への問い合わせが増える。利用制限と両立できるか | ⑦・⑨ |
