# ADR-007: GitHub とトークンはメインプロセスだけが扱い、画面には preload で公開した関数だけを渡す

## ステータス

採用（AI の提案を、2026-11-26 に技術者がレビューして確定）

## コンテキスト

- Electron のアプリは、メインプロセス（Node.js の機能を使える）と画面（レンダラー。Web の画面）に分かれる（ADR-003）
- 画面には GitHub から取った PR のタイトルやコメントの抜粋など、他人が書いた文字列を表示する
- トークンは `repo` スコープ（読み書きを含む）を持ち、漏れたときの影響が大きい（ADR-002）。平文で置かない（N-05）
- Electron のセキュリティの指針では、画面に Node.js の機能を渡さず、メインプロセスとの間を限られた窓口にすることが勧められている（https://www.electronjs.org/docs/latest/tutorial/security ）

## 決定

- GitHub への問い合わせ、トークンの保管と読み出し、手元の保存の読み書き、OS の機能の呼び出しは、メインプロセスだけが行う
- 画面には、preload（contextBridge）で公開した関数だけを渡す。画面からは GitHub にも Node.js の機能にも直接触れない
- 画面では Node.js の機能を使えないようにし、画面とメインプロセスを分けて動かす設定にする（Electron の contextIsolation を有効、nodeIntegration を無効、sandbox を有効）
- 画面とメインプロセスの間の関数（IPC）の形は、⑩.3 で契約として決める

## 理由

- 画面に他人が書いた文字列を表示するため、万一画面に不正なスクリプトが紛れ込んでも、トークンや PC の機能に届かないようにする
- GitHub とのやり取りが1か所に集まり、利用制限の管理（N-04）と「受け取れていない」状態の判定（N-08）を一元化できる
- 画面とメインプロセスの境界が、将来の分担の境界にもなる（container-overview.md 6.）

## 検討した代替案

### 代替案A: 画面から直接 GitHub に問い合わせる（github-prs と同じ）

- メリット: github-prs の処理をそのまま使える。作りが単純
- 採用しなかった理由: トークンを画面に渡すことになる。取り込みや利用制限の管理が画面の表示と絡み、閉じる・切り替えるといった画面の都合に左右される

## 結果（トレードオフ）

- ✓ トークンが画面に出ず、画面に紛れ込んだスクリプトから守れる
- ✓ GitHub とのやり取りが1か所に集まる
- ✗ IPC の契約を決めて保つ手間がある（⑩.3）
- ✗ github-prs の検索の処理は、メインプロセス側に移して使う
