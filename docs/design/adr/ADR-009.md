# ADR-009: 手元の保存は JSON ファイルにし、一時ファイルに書いてから置き換える

## ステータス

採用（2026-11-26 技術者が判断し、文面をレビューして確定）

## コンテキスト

- 受け取った出来事と設定を手元に保存する（ADR-006）。保存の形式は ⑩ で決めることにしていた
- 量は、出来事が1日に数件〜数十件で、30日で多くて千〜2千件（数 MB）。設定は小さい
- 検索・絞り込みは画面のメモリで行う（component-frontend.md）。保存側で検索する必要は無い
- 保存が壊れたら捨てて GitHub から取り直す（Q-09）。暗号化はしない（N-10）
- 出来事を足すのと取り込みの記録を進めるのは、同じ書き込みで行う必要がある（domain-model.md 7. I-5）
- Mac（Apple Silicon・Intel）と Windows 用にビルドする（ADR-008）
- 2026-11-26 に確かめたところ、Electron 45.4.1 の Node.js は 24.22.3 で、`node:sqlite` が使えた

## 決定

- 出来事と取り込みの記録を `events.json`、設定を `settings.json` に置く（場所は Electron の `userData`）
- 書くときは、同じフォルダの一時ファイルに書き、ディスクに書き切ってから名前を置き換える
- 読むときは、`schemaVersion` と zod のスキーマで検査する。合わなければ元のファイルを退避し、空（設定は既定値）から始める
- 詳しくは component-backend.md 7.

## 理由

- 量が少なく、全体を読み書きしても重くない
- 追加の部品が要らない。ネイティブの部品を使わないので、アーキテクチャごとのビルドが簡単なまま
- 出来事と取り込みの記録を1つのファイルに入れれば、置き換え1回で両方が揃って変わる（I-5）
- 壊れたときの扱い（捨てて取り直す）が簡単

## 検討した代替案

### 代替案A: node:sqlite（Node.js に入っている SQLite）

- メリット: 追加の部品が要らない。一部だけを書き換えられ、量が増えても重くなりにくい。トランザクションで I-5 を守れる
- 採用しなかった理由: Node.js では試験的な扱いで、Electron の版を上げたときに変わる可能性がある。今の量では利点が小さい

### 代替案B: better-sqlite3

- メリット: 実績のある SQLite の部品
- 採用しなかった理由: ネイティブの部品のため、Apple Silicon・Intel・Windows ごとに Electron に合わせたビルドが要り、配布物の作り方が複雑になる（ADR-008）

## 結果（トレードオフ）

- ✓ 部品が増えず、配布物の作り方が簡単なまま
- ✓ 書き込みの途中で落ちても、前のファイルが残る
- ✗ 書くたびにファイル全体を書き直す。出来事が増えたら書く回数だけ重くなる（304 のときは書かない）
- ✗ 量が想定より大きく増えたら、代替案A への切り替えを考える。そのときも保存の部品（`main/store`）の中だけで済むようにしておく
