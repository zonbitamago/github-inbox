# ADR-010: GitHub の通知は REST で、出来事への分解と PR の一覧は GraphQL で取る

## ステータス

採用（2026-11-26 技術者が判断し、文面をレビューして確定）

## コンテキスト

- 出来事の起点は GitHub の通知 API（ADR-002）。GitHub の通知 API は REST だけにある
- 出来事は1件のコメント・レビュー・依頼ごとに数えるため、GitHub の通知が指す PR・issue から、前回より後のコメント・レビュー・依頼・アサインを取る必要がある（ADR-002）
- PR の一覧は、既定の期間（7日・50件程度）で5秒以内に出す（Q-02）。自分待ちの理由には、レビューの状態とチェックの結果が要る（business-data.md 2.5）
- 利用制限（Q-04）を守る
- 2026-11-26 に依頼者のアカウントで確かめた結果（github-api.md 3.・5.）
  - GraphQL の timelineItems は、時刻（`since`）と種類で絞れた。3つの PR をまとめて取って1.2秒、利用制限の消費3
  - PR の一覧の項目を GraphQL の1回の検索で全部取ると、7日・52件で6.1秒（5秒を超える）。3つの軽い検索に分けると、それぞれ1〜2秒
  - 利用者が作った open の PR で、GitHub のレビューの判定（reviewDecision）が空だった

## 決定

- GitHub の通知は REST（`GET /notifications`）で取る
- 出来事への分解は GraphQL の timelineItems で、変わったスレッドを1回に20件までまとめて取る。CI の結果だけは REST（ワークフロー実行）で取る
- PR の一覧は、GraphQL の検索を3本（関わった PR・レビュー依頼・自分の open の PR の状態）同時に投げて、結果を合わせる
- レビューの判定が空のときは、レビュアーごとの最新のレビューから判定する（domain-model.md 4.3）
- 使う API と問い合わせの形は github-api.md に書き、ここに無い API は使わない

## 理由

- timelineItems は時刻で絞れて、複数の PR をまとめられるため、問い合わせの回数が少ない
- REST と GraphQL は利用制限が別の枠になり、余裕が増える
- 検索を3本に分けて同時に投げれば、5秒以内に収まる見込み（測った結果）

## 検討した代替案

### 代替案A: REST だけで取る

- メリット: 道具が1種類で済む
- 採用しなかった理由: PR ごとにコメント・レビュー・依頼を別々に取る必要があり、問い合わせの回数が数倍になる。PR の一覧も、レビューとチェックの結果を PR ごとに追加で取ることになり、件数が増えると5秒に収まらない

### 代替案B: PR の一覧を GraphQL の1回の検索で全部取る

- メリット: 問い合わせが1回で済み、作りが簡単
- 採用しなかった理由: 測った結果、6.1秒で5秒を超えた

## 結果（トレードオフ）

- ✓ 問い合わせが少なく、PR の一覧が5秒以内に収まる見込み
- ✓ 利用制限の枠が REST と GraphQL に分かれ、余裕が増える
- ✗ REST と GraphQL の2つの形を扱う。利用制限の管理も2つの枠を見る（component-backend.md 6.）
- ✗ GraphQL の検索・timelineItems の振る舞い（`since` の基準の時刻、チームの読み取りに要るスコープ）は、記録した実際の応答で確かめる必要がある（domain-model.md 10.）
- ✗ Q-04 の目安を GraphQL にも当てはめる（github-api.md 7.）
