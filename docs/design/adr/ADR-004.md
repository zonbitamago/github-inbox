# ADR-004: 認証は利用者が作る classic PAT の貼り付けにする。トークンは safeStorage で暗号化して保存する

## ステータス

採用（2026-11-26 技術者が判断し、文面をレビューして確定。試作の結果を「結果」に反映）

改訂（2026-11-27。CR-007・D-031）: はじめは「OAuth App のデバイスフローを既定にし、classic PAT の貼り付けも選べる」としていた。⑭ の前の確認（build-plan.md 5. の 0-5）で、会社の Organization が OAuth App のアクセス制限を有効にしていると分かり、classic PAT だけにした。改訂の方向は技術者・依頼者が決め、改訂した文面も技術者がレビューして確定した（2026-11-27）

## コンテキスト

- 通知 API は classic のトークンでしか使えず、スコープは `notifications` と `repo` が要る（ADR-002）
- 利用者が自分の GitHub アカウントで認証して使い始められる（F-27）。希望者が手順書を見ずに、アプリの案内だけで使い始められる（F-36・AC-29）
- 認証情報を平文のファイルや URL に置かない（N-05）。github-prs はトークンを URL で渡しており、履歴に残る問題があった
- Organization の管理者の承認は要らない（C-02）。SAML SSO は使っていない（D-019）
- 2026-11-27 に確かめた（CR-007）: 会社の Organization は **OAuth App のアクセス制限**を有効にしている。依頼者が登録した OAuth App のデバイスフローで取ったトークンでは、会社の非公開リポジトリの GitHub の通知が0件（gh CLI では33件）。classic PAT では gh CLI と同じだけ読めた。読めないとき、GitHub はエラーを返さず結果から黙って除く

## 決定

- 認証は、利用者が作った classic PAT（`notifications`・`repo` スコープ）を貼り付ける方法だけにする。アプリは、スコープと説明を入れた作成ページへのリンクを出す（auth-flow.md 3.）
- OAuth App（デバイスフロー）は使わない
- 受け取ったトークンは、Electron の safeStorage（Mac はキーチェーン、Windows は DPAPI）で暗号化してから手元に保存する。画面（レンダラー）には渡さない（ADR-007）

## 理由

- 対象の利用者は全員が会社の Organization の人で、OAuth App では管理者の承認が無いと会社の出来事が取れない。承認を頼むのは C-02 に反する
- classic PAT は会社の Organization で制限されておらず、管理者の承認なしで会社の非公開リポジトリを読める（2026-11-27 に確かめた）
- デバイスフローを選べるまま残すと、選んだ人の会社の出来事がエラー無しで欠け、アプリも利用者も気づけない。それを防ぐ手段が無い
- 依頼者の個人アカウントの OAuth App に頼らなくなる（依頼者が登録を消すと全員が認証し直しになる、という弱みが無くなる）
- safeStorage は OS の保管の仕組みで暗号化するため、平文で置かない（N-05）を満たせる

## 検討した代替案

### 代替案A: OAuth App のデバイスフローを既定にし、classic PAT も選べる（はじめの決定）

- メリット: 利用者がスコープを選んだりトークンを作ったりせず、ブラウザでコードを入れるだけで使い始められる
- 採用しなかった理由: 会社の Organization の OAuth App のアクセス制限で、会社の出来事が取れない（2026-11-27 に確かめた）

### 代替案B: classic PAT を既定にし、デバイスフローも選べるまま残す

- メリット: IPC の契約を変えずに済む。会社が OAuth App を承認すれば、デバイスフローも使える
- 採用しなかった理由: デバイスフローを選ぶと会社の出来事が黙って欠け、防げない。使われない見込みの道を作って保つことになる

### 代替案C: デバイスフローのまま、会社の管理者に OAuth App の承認を頼む

- メリット: 使い始めが一番楽
- 採用しなかった理由: C-02（管理者の承認なしで使える範囲で動く）に反する。承認されるかは会社の事情による

### 代替案D: gh CLI のトークンを使う

- メリット: 認証の画面を作らなくてよい
- 採用しなかった理由: gh を入れてログインしている人に限られる。チームの希望者全員には前提にできない

### 代替案E: OAuth App の Web フロー（ローカルでリダイレクトを受ける）

- メリット: 利用者がコードを入れる手間が無い
- 採用しなかった理由: client secret が要り、公開リポジトリに置けない。手元で受け口を開く仕組みも要る。OAuth App なので、代替案A と同じくアクセス制限も受ける

## 結果（トレードオフ）

- ✓ 管理者の承認なしで、会社の非公開リポジトリの出来事を取れる
- ✓ トークンは暗号化して保存され、画面側には出ない
- ✗ 利用者が GitHub の画面で PAT を作る手間がある（スコープを選び、期限を決め、コピーして貼る）。スコープと説明を入れた作成ページへのリンクで軽くし、手順を画面で示す（F-36 (2)）
- ✗ PAT の作成ページでは、`repo` スコープが「プライベートリポジトリの完全な制御」と表示される。アプリは書き込まないことを、作る前にアプリの画面で説明する（F-36 (2)）
- ✗ 期限切れのときに貼り直しが要る。期限切れは「受け取れていない」表示（N-08）で知らせる
- ✗ PAT をコピーして貼るため、クリップボードの履歴を残すアプリを使っている人では、履歴に PAT が残りうる
- ✗ 署名しないため、Mac では**新しい版を入れ直すたびに、キーチェーンへのアクセスを求めるダイアログが1回出る**（試作で確認。許可すれば読める）。技術者がこれを受け入れた（D-022）。新しい版の初回起動のとき、確認が出る前にアプリで案内する（F-36・AC-42）
- ✓ safeStorage で暗号化したファイルに平文が含まれないことを試作で確かめた
- 実装の注意: Electron 45 では safeStorage の同期版の関数（`encryptString` など）が非推奨。非同期版（`encryptStringAsync` など）を使う
- 会社が後で OAuth App を承認したら、ADR を足してデバイスフローを戻せる（`AuthMethod` に区分値を足す。CR-007）
