# ADR-011: メインプロセスは機能ごとのフォルダに分け、判定は I/O を持たない純粋な関数として core に集める

## ステータス

採用（2026-11-26 技術者が判断し、文面をレビューして確定）

## コンテキスト

- 開発は1人＋AI 1体の直列（D-002）。並列のための分け方は要らない
- 出来事の分解・種類の判定・自分待ちの理由の判定は、取りこぼし・取り違えが S1・S2 を直接損なう（non-functional.md 2.）。単体テストで分岐を網羅する（Q-16、test-strategy.md）
- メインプロセスの仕事は、取り込み・PR の一覧・デスクトップ通知・認証・保存・アプリ（窓・自動起動など）に分かれる（container-overview.md 2.）

## 決定

- メインプロセスのコードを、機能ごとのフォルダ（`ingest`・`pr-list`・`notify`・`auth`・`store`・`app`・`github`・`ipc`・`log`）に分ける
- 判定（出来事への分解・種類・参加中・自分待ちの理由・デスクトップ通知を出すか・URL の検査）は、ネットワーク・ファイル・時計に触れない純粋な関数にして `core` に集める
- 外とつながる所（時計・GitHub への HTTP・ファイル・デスクトップ通知・safeStorage）だけを差し替えられるようにし、入口（`main/index.ts`）で組み立てる
- 詳しくは component-backend.md

## 理由

- 判定を純粋な関数にすると、記録した応答を流すだけで単体テストができ、テスト戦略と合う
- 機能ごとのフォルダなら、1つの機能を直すときに触るフォルダが少ない
- 判定が1か所に集まり、核の不変条件（domain-model.md 7.）を守る場所がはっきりする。AI が実装中に判定を別の場所に書き散らすのを防げる

## 検討した代替案

### 代替案A: 層ごとに分ける（domain／application／infrastructure など）

- メリット: 一般的で、層の決まりが分かりやすい
- 採用しなかった理由: 1つの機能を直すときに、複数の層のフォルダにまたがる。この規模では層を分ける利点が小さい

## 結果（トレードオフ）

- ✓ 判定の単体テストが書きやすい
- ✓ 機能ごとに直す範囲が分かりやすい
- ✗ `core` に何を入れるかの線引きを守る必要がある。⑪ で規約にする（I/O を持つものを `core` に入れない、`core` から他のフォルダを読まない）
