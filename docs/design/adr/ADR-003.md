# ADR-003: Electron + React + TypeScript でデスクトップアプリを作る

## ステータス

採用（2026-11-26 技術者が判断し、文面をレビューして確定。試作の結果を「結果」に反映）

## コンテキスト

- Mac と Windows の両方で動く（N-02）。利用者は依頼者（Mac）とチームの希望者（Mac と Windows が混在）
- 普通のウィンドウを持ち、Cmd+Tab・AltTab アプリ・Alt+Tab の切り替え対象に出る（F-23）。メニューバー・タスクトレイの常駐型にはしない（C-04）
- 軽さより使い心地を優先する。メモリの数値の上限は置かない（acceptance.md NF-04）
- デスクトップ通知・ログイン時の自動起動・認証情報の安全な保管・クリップボードが要る
- 署名はしない（C-03）
- 開発は依頼者 + AI 1体の直列（D-002）。依頼者は React + TypeScript で github-prs を作っている

## 決定

Electron で作り、画面は React + TypeScript、メインプロセスも TypeScript で書く。

## 理由

- Chromium を同梱するため、Mac と Windows で画面の表示がそろう。使い心地を優先する方針（NF-04）に合う
- 必要な機能（デスクトップ通知、ログイン項目、safeStorage、clipboard、外部ブラウザで開く）が Electron の標準の API にある
- Gitify・Slack・VS Code など、同じ形のデスクトップアプリの実績が多い。資料と事例が多く、AI に実装させやすい
- github-prs の React + TypeScript の知識と、検索の処理をそのまま使える
- Mac 用・Windows 用を1つのコードから作れる。1人 + AI の体制で回る

## 検討した代替案

### 代替案A: Tauri + React + TypeScript

- メリット: OS 標準の WebView を使うため、メモリも配布物も小さい
- 採用しなかった理由: Mac（WKWebView）と Windows（WebView2）で表示や挙動が微妙に違いうる。使い心地を優先する方針（NF-04）では、表示がそろうことを重く見た。裏側の処理に Rust が要る場面がある。Windows 版は Windows 上（または CI）でビルドする必要がある

### 代替案B: OS ごとにネイティブで作る（Mac は Swift、Windows は C#）

- メリット: 最も軽く、OS になじむ
- 採用しなかった理由: 同じ機能を2回作ることになり、1人 + AI の体制では重い

## 結果（トレードオフ）

- ✓ Mac と Windows で表示がそろい、1つのコードで済む
- ✓ 必要な OS の機能が標準の API でそろう
- ✗ メモリは数百 MB、配布物は100MB 前後になる（NF-04 では上限を置かないとした）
- ✓ 署名しない（ad-hoc 署名の）アプリでも、Mac ではデスクトップ通知・クリックで前面・Cmd+Tab／AltTab・自動起動・safeStorage・閉じたら終了が動くことを試作で確かめた（review/spike-unsigned-electron-mac.md）
- ✗ デスクトップ通知は、アプリがアプリケーションフォルダにあることが前提。一時フォルダやダウンロードしたままの場所から開くと、許可も求められずに失敗する（アプリが初回にアプリケーションフォルダへの移動を勧める。F-36・D-024）
- ✗ ad-hoc 署名と Hardened Runtime の組み合わせで起動に失敗しうるという警告がビルド時に出る（試作では起動できた）。配布物を作る設定は ⑪ で決める → ⑪ で Hardened Runtime を入れたままにすることにした（トークンの保護のため。build-and-release.md 2.。⑭ で起動を確かめる）
- ✗ **Windows での振る舞いは確かめていない**（D-021。⑫ のリスク登録簿に残す）
- ✗ Electron の更新に追従する手間がある（セキュリティの修正を取り込むため）
