# ADR-002: 出来事の起点を GitHub の通知 API にし、classic のトークン（notifications・repo スコープ）で読み取る

## ステータス

採用（2026-11-26 技術者が判断し、文面をレビューして確定）

## コンテキスト

出来事（business-data.md 2.1）を、発生から5分以内に（N-01）、GitHub の利用制限にかからずに（N-04）受け取る必要がある。出来事は1件のコメント・レビュー・依頼ごとに数える（D-011）。参加中の PR への発言（F-02）や、自分が起動した GitHub Actions の結果（F-05）も扱う。

GitHub の通知 API について、次のことを確かめた（https://docs.github.com/en/rest/activity/notifications ）。

- 通知はスレッド（PR・issue などの議論）単位で返り、理由（reason）が付く。理由は出来事の種類とほぼ対応する: `review_requested`（レビュー依頼。チーム宛てを含む）、`author`（自分が作ったスレッド）、`comment`（自分がコメントしたスレッド）、`mention`、`team_mention`、`assign`、`ci_activity`（自分が起動した GitHub Actions の完了）
- 理由はスレッド単位で、後の通知で変わりうる
- 差分の問い合わせ（`Last-Modified` / `If-Modified-Since`）に対応し、変化が無いときの 304 は利用制限に数えられない（⑬ で確かめると、304 になるのは `ETag` / `If-None-Match` のときだけだった。CR-003）。`X-Poll-Interval` で問い合わせの間隔が指定される
- 通知 API は classic のトークンでしか使えない（"These endpoints only support authentication using a personal access token (classic)."）。スコープは `notifications` または `repo`。会社のプライベートリポジトリの PR・issue の中身を読むには `repo` が要る。依頼者の gh CLI の OAuth トークンでも、通知 API を読めることを確かめた
- 依頼者のデータでは、直近7日に `ci_activity` の通知が0件だった。各自の GitHub の通知設定に左右されることを示している

## 決定

- 出来事の起点は、利用者宛ての GitHub の通知（通知 API）にする。通知の理由で対象を選び、個々の出来事（コメント・レビュー・CI の結果）は、通知が指す PR・issue・ワークフローから追加で取る
- 認証は classic のトークン（はじめは OAuth App のトークンまたは classic PAT。2026-11-27 から classic PAT だけ。ADR-004・CR-007）で、スコープは `notifications` と `repo` にする。アプリは GitHub に書き込まない（N-06）
- PR の一覧（F-15）は、github-prs と同じく検索 API（`involves:@me`）で取る。出来事とは別の取り込み口とする

## 理由

- 「自分に関わるか」の判定を GitHub に任せられる。理由が出来事の種類とほぼ対応し、自前で判定するより作り込みが小さい
- 差分の問い合わせで、変化が無いときは利用制限を減らさない。5分以内（N-01）と利用制限（N-04）を両立しやすい
- 自分自身の操作は GitHub が通知しないため、AC-08（自分の操作は出来事にしない）と合う
- 既製品の Gitify も同じく通知 API を起点にしており、実績のある方式である

## 検討した代替案

### 代替案A: 検索 API や PR の履歴を自前で走査して判定する

- メリット: 各自の GitHub の通知設定に左右されない。読み取り専用のトークン（fine-grained PAT など）を使える余地がある
- 採用しなかった理由: 「自分に関わるか」の判定（メンション・参加中・レビュー依頼など）を自前で作る必要があり、作り込みが大きい。問い合わせ回数が大幅に増え、検索 API は制限が厳しい。5分以内と利用制限の両立が難しい

### 代替案B: GitHub の Events API（受け取ったイベント）を使う

- メリット: リポジトリの活動を広く取れる
- 採用しなかった理由: GitHub のドキュメントで、即時の用途向けではなく、遅延が30秒〜6時間になりうるとされている（"This API is not built to serve real-time use cases."、https://docs.github.com/en/rest/activity/events ）。Watch やフォローに基づき、「自分に関わる」とは範囲が違う

### 代替案C: Webhook を受ける

- 採用しなかった理由: ADR-001 のとおり、自前のサーバーを置かない

## 結果（トレードオフ）

- ✓ 判定を GitHub に任せ、作り込みを小さくできる
- ✓ 変化が無いときの問い合わせは利用制限を減らさない
- ✗ 各自の GitHub の通知設定に左右される。特に CI の結果は、Actions の通知を「on GitHub」にし、「失敗したものだけ」をオフにしておく必要がある。アプリの初回の案内（F-36）で案内する（D-019・D-024）
- ✗ トークンの `repo` スコープは読み書きを含む。アプリは書き込まないが、トークンが漏れたときの影響は大きい。保管（N-05）の強さを ⑨ で決める
- ✗ fine-grained PAT や GitHub App のトークンは使えない
- ✗ 通知はスレッド単位にまとまり、理由も変わりうる。1件ずつの出来事への分解と種類の判定のため、追加の問い合わせと判定の作り込みが要る（⑩.1・⑩.3）
