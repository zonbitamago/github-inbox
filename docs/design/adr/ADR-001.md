# ADR-001: 自前のサーバーを置かず、各自の PC のアプリが直接 GitHub に問い合わせる

## ステータス

採用（2026-11-26 技術者が判断し、文面をレビューして確定）

## コンテキスト

自分に関わる出来事に、発生から5分以内に気づけるようにする（intent.md S1、requirements.md N-01）。GitHub から出来事を受け取る方法は、大きく「GitHub から本システムへ知らせてもらう（Webhook）」と「本システムから GitHub に問い合わせる（ポーリング）」の2つがある。

- Webhook を受けるには、受け口となるサーバーが要る。各自の PC は外から直接つながれない
- Organization に Webhook や GitHub App を設定するには、Organization の管理者の操作が要る。要件では、管理者の承認なしで使える範囲で動くことにしている（requirements.md C-02）
- 利用者は依頼者とチームの希望者（10人前後）で、各自の GitHub アカウントで使う（D-005）。運用の担い手は依頼者1人（D-002）

## 決定

自前のサーバーは置かない。各自の PC で動くアプリが、各自の GitHub アカウントの認証で、GitHub に直接問い合わせる。

## 理由

- 管理者の操作が要らない（C-02 を守れる）
- サーバーの置き場所・費用・運用・障害対応が要らない。運用の担い手が1人でも回る
- 5分以内（S1）は、ポーリングでも満たせる見込みがある。GitHub の通知 API は差分の問い合わせ（`Last-Modified`。⑬ で `ETag` に変えた。CR-003）に対応し、変化が無いときの応答（304）は利用制限に数えられない（ADR-002）
- 利用者ごとに認証が独立し、他人の出来事を扱わない。サーバーに他人の認証情報を預けずに済む

## 検討した代替案

### 代替案A: 自前のサーバーで Webhook を受け、各自の PC に中継する

- メリット: 出来事がほぼ即時に届く。GitHub への問い合わせ回数が減る
- 採用しなかった理由: Organization への Webhook や GitHub App の設定に管理者の操作が要る（C-02 に反する）。個人・OSS のリポジトリ（D-019）には Webhook を設定できない。サーバーの置き場所・運用・認証情報の預かりが要る

### 代替案B: 共有のサーバーで全員分をまとめて問い合わせる

- メリット: 問い合わせをまとめられる
- 採用しなかった理由: サーバーに全員の認証情報を預けることになる。サーバーの運用が要る。10人前後なら、各自の利用制限の枠で足りる見込み

## 結果（トレードオフ）

- ✓ 管理者の操作もサーバーの運用も要らない。配布して各自が入れれば使える
- ✓ 認証情報は各自の PC の中だけにある
- ✗ 届くまでの速さは問い合わせの間隔で決まり、即時にはならない（5分以内に収まるかを ⑨ で確かめる）
- ✗ アプリが立ち上がっていない間は受け取らない（requirements.md F-24・F-06 で承知済み）
- ✗ 各自の利用制限（1時間あたり5,000回。gh CLI など同じアカウントの他の道具と共有）の中でやりくりする
