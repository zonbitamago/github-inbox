# ADR-005: 個人の public リポジトリで開発し、GitHub Actions でビルドして GitHub Releases で配る

## ステータス

採用（2026-11-26 技術者が判断し、文面をレビューして確定）

## コンテキスト

- Mac 用・Windows 用の配布物を作り（F-29）、希望者がダウンロードできる場所に、短い説明（初回の OS の警告の越え方・対応 OS）と一緒に置く（F-30）
- 新しい版が出たことをアプリが知らせる。入れ直しは各自（F-31、自動更新はしない W-07）
- 署名はしない（C-03）
- 開発する PC は Mac。Windows 用の配布物も作る必要がある
- 依頼者は github-prs を個人の public リポジトリで公開している

## 決定

- ソースコードは依頼者の個人アカウントの public リポジトリに置く
- GitHub Actions で Mac 用・Windows 用の配布物をビルドし、GitHub Releases に置く
- アプリは、公開リポジトリの最新のリリースを見て、新しい版があるかを確かめる（F-31）

## 理由

- 希望者は GitHub のアカウントを持っており、Releases からそのままダウンロードできる。共同作業者に加える手間も無い
- public リポジトリでは、GitHub Actions の標準のランナーを無料で使える。Mac と Windows の両方のランナーでビルドでき、開発する PC が Mac だけでも Windows 用を作れる
- 新しい版の確認に、別の置き場所や仕組みが要らない
- github-prs と同じ公開の仕方で、依頼者が慣れている

## 検討した代替案

### 代替案A: 会社の Organization のリポジトリ

- メリット: コードと記録が社外に出ない
- 採用しなかった理由: 依頼者が個人の public リポジトリを選んだ。Actions の利用分が Organization の枠になる

### 代替案B: 個人の private リポジトリ

- メリット: コードと記録が公開されない
- 採用しなかった理由: 希望者を共同作業者に加えないとダウンロードできない。Actions の利用分に上限がある

### 代替案C: 社内のファイル共有に置く

- メリット: 社内に閉じる
- 採用しなかった理由: ビルドと新しい版の確認を別に用意する必要がある

## 結果（トレードオフ）

- ✓ 置き場所・ビルド・新しい版の確認が GitHub だけで完結する
- ✓ 開発する PC が Mac だけでも Windows 用を作れる
- ✗ **コードと `docs/`（要件定義の記録を含む）が公開される**。会社名・Organization 名・社内の事情・実データを書かない。最初に push する前に `docs/` を見直す（container-overview.md 5.）
- ✗ 誰でもダウンロードして使える（使うには各自の GitHub アカウントでの認証が要る）
- ✗ 署名しないため、ダウンロードした配布物を開くときに OS の警告が出る（配布ページの短い説明で案内する。F-30・C-03）
