## 1. 方針

- **メインプロセス**（取り込み・判定・保存・利用制限の管理）は、GitHub への問い合わせと判定の処理を切り離し、判定の処理を純粋な関数として**単体テストを厚く**する（テストピラミッド寄り）
- **画面**（React）は、品質保証フレーム 6.3節の Testing Trophy に従い、**静的解析と結合テスト（Testing Library）を主にする**
- **OS との結合**（デスクトップ通知・クリックで前面・切り替え・自動起動・キーチェーン・Gatekeeper）は自動化しにくいため、**手動のチェックリスト**で確かめる（試作のチェックリストを再利用する）
- GitHub の実物には CI からつながない。**記録した応答をもとにした模擬の GitHub**で確かめ、実物では依頼者のアカウントで最後に確かめる
- リポジトリは公開する（ADR-005）。**テストのデータ（模擬の応答）は架空のもの**にし、会社名・Organization 名・実際の PR やコメントを入れない

## 2. テストの層

| 層 | 対象 | 道具（⑪ で確定。書き方は [test-conventions.md](../conventions/test-conventions.md)） | 量 | 主に確かめる品質特性 |
| --- | --- | --- | --- | --- |
| 静的解析 | 全体 | TypeScript（strict）、ESLint | 常に | 保守性、型の食い違い |
| 単体 | メイン: 通知から出来事への分解、種類の判定、自分待ちの理由の判定、問い合わせの間隔と回数の管理（偽の時計）、保存（古い出来事の削除）、URL の検査、ログに書かないもの／画面: 表示の整形、絞り込みの処理 | Vitest | 多い | 機能正確性、時間効率性（間隔）、機密性 |
| 結合（メイン） | 模擬の GitHub につないだ取り込み → 保存 → IPC の流れ。失敗（ネットワーク・認証切れ・利用制限）、取り戻し、壊れた保存からの立ち直り、問い合わせの回数 | Vitest + 模擬の HTTP サーバー（MSW など） | 中 | 機能完全性、障害許容性、回復性、資源効率性 |
| 結合（画面） | 出来事の一覧・PR の一覧・設定・初回認証・受け取れていない表示を、IPC を模して利用者の操作で確かめる | Vitest + Testing Library | 多い（画面の主戦場） | 運用操作性、機能正確性 |
| 契約 | 画面とメインプロセスの間の IPC の形。共有の型に加え、メインプロセス側で受け取った値を検査する | 共有の型 + 実行時の検査（zod など） | 少ない | 相互運用性（画面とメインのずれ） |
| E2E | 重要な流れ（立ち上げて一覧が出る、出来事を受け取って一覧に載る、PR をリロードする、設定を変える、受け取れていない表示）。模擬の GitHub を使う | Playwright（Electron 対応） | 少ない（5本程度） | 運用操作性、障害許容性 |
| 手動（OS との結合） | デスクトップ通知とクリック、Cmd+Tab・AltTab、自動起動、閉じたら終了、キーチェーンの確認、Gatekeeper、ダークモード、デスクトップ通知の失敗の表示 | 試作のチェックリスト（review/spike-unsigned-electron-mac.md 3.）を拡張 | 版ごと | 運用操作性、適応性 |
| 実データでの確認 | 依頼者のアカウントで、出来事の取り込み（種類ごと）、PR の一覧の速さ、1時間の利用制限の消費、8時間の連続稼働 | 手動 + アプリのログ | ⑮ で1回、版ごとに要点 | 機能完全性、時間効率性、資源効率性 |
| 受け入れ（UAT） | acceptance.md の AC-01〜43 を依頼者が確かめる | acceptance.md | ⑮ | 利用時品質 |
| 事後確認 | S1・S2（acceptance.md 3.） | 実データ | リリースの2〜4週間後 | 利用時品質 |

## 3. CI

- push・PR ごと: 静的解析、単体、結合、契約、依存パッケージの脆弱性の検査（GitHub Actions）
- E2E: Mac のランナーで実行する（時間がかかる場合は main への push のときだけ）
- タグを付けたとき: Mac 用・Windows 用の配布物をビルドして Releases に置く（ADR-005。詳細は [build-and-release.md](../conventions/build-and-release.md)）

## 5. テストの順番（実装で守ること）

- 判定の処理（出来事の分解・種類・自分待ちの理由）は、**先にテストを書いてから**作る。区分値は business-data.md から取り、新しく作らない
- GitHub の応答の形が分からないときは、推測で模擬の応答を作らず、実際の応答を（架空のデータに置き換えて）記録してから使う
- OS との結合は、アプリケーションフォルダに置いたビルドで確かめる（一時フォルダからはデスクトップ通知が失敗する。試作で確認）
